# Проверка строгого профиля PIX опытом

Наш валидатор `pix_spec_checker.py` останавливает выгрузку по правилам, часть
которых — гипотезы. Они взяты не с потолка: одни сверены с эталонным каталогом
студии, другие воспроизводят её же сообщения об отказах. Но несколько правил
(жёсткие префиксы неймспейсов, обязательные `processType` и `isExecutable`,
только целые координаты) держатся на договорённости команды, а не на
наблюдении. Проверить их без исходников студии можно только опытом.

Этот набор ставит опыт: восемь файлов, каждый отличается от заведомо исправного
ровно одним отклонением. Импортируете по одному — получаете ответ отдельно по
каждому правилу.

**Зачем это нужно.** Лишнее правило так же вредно, как пропущенное: оно
останавливает выгрузку карты, которую студия приняла бы. После опыта каждое
правило либо подтверждается, либо снимается — и валидатор перестаёт быть
набором предположений.

---

## Что понадобится

* PIX Процессная студия на рабочей машине;
* Python 3.10+ (тот же, на котором работает бэкенд);
* полчаса: восемь импортов по паре минут.

---

## Шаг 1. Сгенерировать пробы

```
cd backend
venv\Scripts\python.exe scripts\pix_probe\generate_pix_tests.py
```

Файлы лягут в `scripts\pix_probe\pix_test_suite\`. Скрипт сам себя проверяет и
печатает таблицу — вот что в ней важно:

| Столбец | Что означает |
|---|---|
| `откл.` | Сколько мест в файле отличается от контроля. Должно быть `1`; у пробы с префиксом — `весь` (префикс стоит в каждом теге, иначе отклонение не внести) |
| `по стандарту` | Принимает ли файл обычная проверка BPMN 2.0 |
| `профиль PIX` | Отвергает ли его наш строгий профиль |
| `правило` | Какое правило проверяется этой пробой |

Последняя строка вывода должна быть **«Самопроверка пройдена»**. Если вместо неё
«НАБОР НЕ ГОДЕН К ОПЫТУ» — сломан инструмент, а не студия: несите вывод
разработчикам, импортировать нечего.

### Что в наборе

| Файл | Отклонение | Вопрос к студии |
|---|---|---|
| `test_00_baseline.bpmn` | **нет** | Контроль |
| `test_01_custom_namespace.bpmn` | префикс `mybpmn:` вместо `bpmn:` | Читает по URI (как велит стандарт) или по префиксу? |
| `test_02_float_coordinates.bpmn` | дробные числа в `dc:Bounds` | Требует `int` вместо `double`? |
| `test_03_missing_process_type.bpmn` | нет `processType` | Требует необязательный по стандарту атрибут? |
| `test_04_missing_is_executable.bpmn` | нет `isExecutable` | То же |
| `test_05_unlinked_shape.bpmn` | `BPMNShape` на несуществующий элемент | Откажет или упадёт с `NullReferenceException`? |
| `test_00_baseline.pmm` | **нет** | Контроль |
| `test_06_pmm_out_of_bounds.pmm` | шаг за границей дорожки | Обрежет, перенесёт или откажет? |
| `test_07_pmm_unknown_type.pmm` | тип фигуры не из каталога | Ожидается «Notation element not found» |

Рядом с каждым `.pmm` лежит `.map.xml` — та же карта распакованной, чтобы
глазами увидеть, что именно изменено.

## Шаг 2. Найти журналы студии

```
venv\Scripts\python.exe scripts\pix_probe\log_analyzer.py locate
```

Скрипт обходит вероятные места (`%LOCALAPPDATA%\PIX Robotics\PIX Studio\Logs` и
соседние) и показывает, что нашлось.

**Точный путь у нас не подтверждён** — эталонной установки студии у команды
разработки нет, список мест построен по тому, как обычно устроены приложения
.NET под Windows. Если `locate` ничего не нашёл, это нормально:

* в самой студии поищите пункт «Открыть папку с логами» или подобный;
* посмотрите каталог установки (`C:\Program Files\PIX Robotics\...`);
* загляните в «Просмотр событий» Windows → Журналы Windows → Приложение,
  отфильтровав по источнику PIX.

Найденный путь передаётся один раз через `--logs`, дальше запоминается.

## Шаг 3. Импортировать пробы по одной

Порядок для каждого файла — три действия. **Начинайте с контроля.**

```
:: 1. снимок журналов ДО импорта
venv\Scripts\python.exe scripts\pix_probe\log_analyzer.py begin test_00_baseline.bpmn --logs "C:\...\PIX Studio\Logs"

:: 2. руками: откройте студию и импортируйте
::    scripts\pix_probe\pix_test_suite\test_00_baseline.bpmn

:: 3. запишите, чем кончилось
venv\Scripts\python.exe scripts\pix_probe\log_analyzer.py end --result ok --note "Карта открылась, одна дорожка, три фигуры"
```

`--result` принимает три значения, и различать их важно:

| Значение | Когда ставить |
|---|---|
| `ok` | Карта открылась. Даже если что-то выглядит не так — это `ok` плюс `--note` с описанием |
| `refused` | Студия показала сообщение об ошибке и не открыла карту |
| `crash` | Приложение закрылось или показало необработанное исключение |

Дальше — остальные семь файлов тем же порядком (`--logs` больше не нужен).

> **Если контроль не импортировался**, останавливайтесь. Дело не в правилах, а в
> самой пробе: не та версия студии, не тот пункт меню, пустой каталог нотаций.
> Разберитесь с этим — иначе остальные семь результатов ничего не значат.

**Между пробами студию перезапускать не нужно**, но и держать открытыми
несколько импортов сразу не стоит: инструмент относит прирост журнала к
последней начатой пробе.

## Шаг 4. Забрать сводку

```
venv\Scripts\python.exe scripts\pix_probe\log_analyzer.py report
```

```
проба                                  студия     правило профиля              вывод
────────────────────────────────────────────────────────────────────────────────────
test_00_baseline.bpmn                  ok         —                            контроль в порядке
test_07_pmm_unknown_type.pmm           crash      pix_pmm_type_unknown         правило ПОДТВЕРЖДЕНО (KeyNotFoundException)
test_02_float_coordinates.bpmn         ok         pix_bounds_not_integer       правило ЛИШНЕЕ: студия приняла файл
```

Что с этим делать:

* **правило ПОДТВЕРЖДЕНО** — оставляем как есть; в `pix_spec_checker.py` у этого
  правила источник меняется с `required` на `observed`, и в комментарий
  дописывается точное сообщение студии.
* **правило ЛИШНЕЕ** — понижаем до `warning` или убираем совсем. Держать
  ошибкой то, что студия принимает, значит зря останавливать людям выгрузку.

Всё сырое лежит рядом:

* `probe_results\session.json` — результаты и разобранные исключения;
* `probe_results\raw\<проба>.log` — ровно то, что студия дописала в журнал за
  время импорта. Именно этот файл прикладывайте к задаче на исправление.

---

## Что отдать разработчикам

1. `probe_results\session.json`
2. Каталог `probe_results\raw\`
3. Снимки экрана с текстом ошибок студии — сообщение на экране и запись в
   журнале не всегда совпадают, а правило надо связать с тем, что видит человек.

По этим трём вещам правила профиля правятся точно, без догадок.
